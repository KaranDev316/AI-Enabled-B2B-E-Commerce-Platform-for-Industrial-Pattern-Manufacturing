# S03 implementation review

Date: 22 November 2026. Reviewed revision: `ecc81b7`. Existing untracked S01/S02 reports were preserved. This task adds only this report; application files, configuration, dependencies, and reference assets were not edited.

**Assessment: the persisted public catalogue is implemented, but S03 should remain open.** Backend active-product reads and image visibility have useful automated coverage. Frontend scope, mobile navigation, live-detail consistency, image presentation, and incomplete acceptance evidence need attention.

## What S03 was supposed to deliver

Sources: [CONTEXT](../CONTEXT.md), [master PRP](../PRP.md), [PRP-002](../PRPs/002-public-catalogue-and-products.md), [S03 slice specification](../VERTICAL_SLICE_PLAN.md#s03--browse-the-persisted-public-catalogue), and [verification obligations](../VERIFICATION_PLAN.md#12-verification-obligations-for-remaining-slices).

A visitor opens company information, browses/searches/filters active persisted products, inspects the correct product and specifications, and chooses an RFQ entry point. An unauthenticated visitor reaches login without automatically submitting anything. Catalogue prices are indicative; absent prices say on request. The public catalogue is shared with Customers.

Loading, empty catalogue, no matching results, unavailable service, and inactive/unknown product must be distinguishable. Correct product images should retain their aspect ratio and have an honest missing-image fallback. Product imagery must remain separate from private customer documents. Controlled persisted fixtures support the demonstration until Admin writes arrive.

S03 covers REQ-05, image-display portions of REQ-07, AC-02-01/02/03, and the valid-image display portion of AC-02-06. Admin maintenance/upload belongs to S04; actual RFQ submission belongs to S05. Cart, checkout, recommendations, specification-PDF generation, and invented catalogue facts are excluded.

## What is good

1. Live catalogue data comes from the database. Sample preview records are explicitly labeled and are not silently substituted after API errors or empty responses.
2. Inactive/unknown products are denied by the backend, including image access for inactive products. Numeric compatibility links are guarded against oversized IDs.
3. List and detail share the response schema and persisted category/specification/image associations. The S03 backend test asserts equality for the same product.
4. Category/material filters derive options from available records rather than invented category counts. Clear Filters resets search and filters; search/filter changes reset pagination.
5. List prices distinguish indicative amounts from official quotations and handle missing values honestly.
6. Initial loading, empty, no-results, error/retry, and unavailable-product states are separate. Missing images have a fallback rather than a fabricated product picture.
7. Existing public routes and components remain in use. Source retains the reference's navy/orange public identity, catalogue filter/sidebar and card layout. This is a source/reference observation, not a rendered visual pass.

## What is wrong or incomplete

### Medium — specification-PDF generation contradicts approved scope

Both landing capability details and catalogue product details expose “Download PDF Specifications,” implemented by `frontend/src/data/downloadSpecifications.js`. PRP-002 explicitly excludes specification-PDF generation. Its appearance in the historical mockup cannot override the requirements.

The generated summary includes fallback statements, and the implementation is a single-page text PDF that strips non-ASCII characters. Those limitations are secondary: the feature itself is outside S03's approved scope.

**Suggestion:** remove the unsupported operation in a separately authorized implementation task while preserving the approved details structure. Do not expand the generator merely to make an excluded feature more complete.

### Medium — public header lacks the reference's mobile navigation behavior

The inspected mobile landing reference uses compact logo/menu navigation. Current `PublicHeader` always renders desktop links/actions and contains no menu toggle. Its `public-site-*` classes have desktop grid/flex rules, while responsive rules in `LandingPage.css` target the older `public-navigation` and `public-nav-actions` classes.

This is a source-confirmed responsive implementation gap and likely causes cramped navigation/overflow on narrow screens. Exact overflow and touch behavior were not measured in a browser.

**Suggestion:** adapt the established public header to the supplied mobile reference and test menu keyboard/touch use at narrow widths. Keep the existing public navigation destinations and visual identity.

### Medium — refreshed catalogue can disagree with open details

The modal stores the selected product object in `selectedProduct`. Background refresh replaces `products` but does not update or clear that object. Renaming/editing/deactivating a product can therefore update/remove its card while leaving old modal details and RFQ action visible. Backend action-time checks may still reject invalid selection; this finding does not establish an RFQ authorization bypass.

Pagination also remains on its old page after refresh. If the active dataset shrinks below that page, `filtered.length` remains positive but the page slice can be empty, with a range such as “Showing 7–6 of 6 patterns.” These are source-derived outcomes, not executed browser reproductions.

**Suggestion:** resolve selection by ID against refreshed records, show an honest unavailable state when removed, and clamp pagination after dataset changes. Test updates/deactivation while modal and later pages are open.

### Medium — background failures can look like successful synchronization

`loadProducts({ quiet: true })` suppresses failures and retains the old ready state. `useKpcLiveSync` displays “Live Synced” before awaiting refresh, so an event-triggered failed refresh can still show success. This compromises the requirement to distinguish unavailable data and truthful state.

**Suggestion:** retain readable prior data with an explicit refresh-failed/stale state, and show synchronization success only after successful resolution. Reuse existing feedback styles instead of adding decorative status UI.

### Medium — live specification structure is only partly reflected in the detail table

The API/model exposes `specifications` as a string. The detail component maps table rows from an array only, so live stored specifications appear as a separate text block while most table rows use generic “to be confirmed” text. Preview arrays populate a richer table than live records can provide. Stored facts are not wholly lost, but the main specification table does not reliably present the actual persisted details in the same manner as preview content.

**Suggestion:** align the details presentation with the supported persisted contract. Clearly label unavailable facts and preserve stored text; do not invent parsed values or introduce a new schema solely to copy mockup numbers.

### Lower priority — price, images, and navigation need tightening

- Cards display indicative price/on-request, but `ProductDetails` does not display `indicative_price`; it always says price/lead time come from quotation. Add the same clearly indicative price/on-request treatment to details for consistent browsing.
- Image containers use fixed aspect ratios and `overflow: hidden`, while images use full width and automatic height. A tall source can be clipped despite `object-fit: contain`, because the image box itself is not bounded to the container. Test portrait/landscape sources and contain the whole product image without distortion.
- Selecting a thumbnail then navigating between direct detail routes does not reset `imageIndex`; the new product can show an image fallback even when it has a first image. Reset selection per product and when images shrink.
- `/catalogue` renders the catalogue but the header marks Home active because its check recognizes only `/products`. Correct the active marker for the existing alias.
- The catalogue initial error is retryable, but unknown product and service failure do not have normalized backend code/message errors. This inherits the shared error-contract inconsistency; do not present a missing record as an outage.
