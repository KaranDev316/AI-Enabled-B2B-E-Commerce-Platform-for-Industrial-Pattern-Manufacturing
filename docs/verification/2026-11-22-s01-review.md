# S01 implementation review

Date: 22 November 2026. Reviewed revision: `ecc81b7`. Initial working tree was clean. This review adds only this report; no application, configuration, dependency, design, or existing documentation files were edited.

**Assessment: the core S01 functionality is implemented, but S01 should remain open.** Basic backend authentication tests pass. The current browser authentication design departs from the approved cookie contract, logout can falsely appear successful, validation responses expose submitted password input, and full acceptance evidence is missing.

## What S01 was supposed to deliver

The governing sources are [CONTEXT](../CONTEXT.md), [the master PRP](../PRP.md), [PRP-001](../PRPs/001-accounts-and-access.md), [S01 in the slice plan](../VERTICAL_SLICE_PLAN.md#s01--sign-in-enter-the-correct-portal-and-sign-out), and [the verification contract](../VERIFICATION_PLAN.md).

An active Customer, Employee, or Admin signs in, reaches only the permitted portal, retains authentication through normal navigation and refresh, and signs out. Wrong credentials and inactive accounts receive the same generic failure. Expired or revoked sessions cannot authorize protected requests.

The implementation scope includes:

- Python 3.12/FastAPI and Node 24/React foundation, relative API requests, and a Vite development proxy preserving browser Origin.
- PostgreSQL users/sessions, initial Alembic migration, Argon2id password hashes in `VARCHAR(255)`, initial Admin provisioning, and controlled other-role demo identities.
- Server role guards, login session rotation, configurable expiry, and server-side logout revocation.
- HttpOnly, SameSite=Lax cookies, Secure on HTTPS, trusted-Origin checks on mutations including login, and session-bound CSRF for authenticated mutations.
- Minimal portal shells with useful loading, denied, validation, and service-failure states.
- Isolated database verification, CI, frontend build, migration/persistence evidence, and a hosted HTTPS demonstration.

S01 owns REQ-02, AC-01-03, AC-01-05, and the logout/expiry portion of AC-01-04. Registration, profile editing, employee management, and reset/change-password workflows belong to S02. Later business screens do not count as evidence that S01 is complete.

## What is good

1. Authorization is enforced on the server, independently of hidden links or frontend role state. The active-role workspace matrix is covered by tests.
2. Passwords are hashed with Argon2id, exact password matching is retained, and wrong-password/nonexistent/inactive-account responses are generic.
3. Sessions remain server-managed records with expiry and revocation. This is a sound foundation even though their browser transport needs correction.
4. Origin and session-bound CSRF checks exist, and tested rejected logout requests preserve the valid session.
5. Migration-before-startup and repeat-startup CI checks improve deployment reliability. The earlier report's statement that CI never runs migrations is now outdated.
6. Relative API requests and the approved local proxy ports are preserved. Private file downloads explicitly use the tab bearer token with cookies omitted, reducing file identity ambiguity; this does not establish correctness of the wider mixed-auth design.

## What is wrong or incomplete

### High — session credentials are readable by browser JavaScript

Evidence: `backend/app/api/auth.py` returns the session ID as both `token` and `session_token` on login and `/me`; `frontend/src/context/AuthContext.jsx` saves it as `kpc_auth_token`; `frontend/src/utils/fetchInterceptor.js` attaches it as a bearer credential. `backend/app/dependencies.py` accepts bearer credentials before cookies.

This conflicts with the documented HttpOnly-cookie authentication design and the verification requirement that authentication secrets stay out of browser storage. Although the cookie itself is HttpOnly, returning the same credential in JSON makes it available to JavaScript. A script injection could extract that credential. No script injection or account compromise was tested or established here.

**Suggestion:** reconcile the implementation with the approved authentication contract. Prefer cookie-based browser authentication and stop returning/storing session IDs. If simultaneous different-role tabs are a required product decision, explicitly revise the authentication requirements and verification contract before treating the bearer design as accepted. Preserve the approved UI and deployment routing.

### High — failed logout is presented as successful

`AuthContext.logout()` does not inspect `response.ok`, catches network errors, and always clears local identity in `finally`. Both portal layouts then proceed to login; the Customer layout's error handler cannot detect these swallowed failures.

A rejected request or outage can leave the server session usable while the UI appears signed out. This is source-confirmed; browser failure injection was not run.

**Suggestion:** confirm revocation before reporting success, propagate failures to the existing logout error state, and offer retry. Test 403, server error, network failure, successful retry, and replay of the old credential.

### High — validation responses echo submitted password input

An isolated current-revision HTTP probe submitted a synthetic marker inside a password array. The endpoint returned **422**, the marker appeared in the response, and `detail` was a list rather than the normalized error structure required by CONTEXT. The database dependency was overridden with `None`; the invalid request did not reach credential lookup or a real database.

The existing malformed-login test asserts only status 422 and misses this confidentiality defect.

**Suggestion:** normalize request-validation errors and remove submitted secret values from responses and logs. Add assertions for password omission, safe code/message/field feedback, and no session creation.

### Medium — bearer authentication and cookie rotation disagree

Login reads only the cookie when deciding which session to replace, whereas identity resolution/logout prefer the bearer header. `rotate_session` also deletes the previous cookie session only when it belongs to the new login's user, committing that deletion separately from creation.

Consequences requiring verification: bearer-only re-login can leave the old credential active; switching accounts can retain the former session; separate tabs send their own bearer token while sharing the latest cookie. Existing rotation tests cover only same-user cookie re-login and database-row replacement, not this mixed browser behavior. This is a source-derived risk, not a demonstrated cross-account data leak.

**Suggestion:** use one coherent browser session model, define account-switch/re-login revocation explicitly, and test old/new credentials directly. Make replacement transactional so creation failure cannot leave a partially completed rotation.

### Medium — stale authenticated state and service failures lack recovery

`AuthContext` validates on initial mount only when a stored token exists. The fetch interceptor adds headers but has no shared 401 recovery. `ProtectedRoute` subsequently trusts in-memory identity. The generic portal layout can continue displaying “Session Active · Server Verified” after backend expiry or revocation.

Initial session lookup also treats non-OK responses as signed out, and network failure clears in-memory identity without a service-error/retry state. Cached user data with no token can remain trusted locally because the no-token mount path does not clear that user. Backend guards still apply; this is not evidence of backend privilege escalation.

**Suggestion:** clear stale identity on definitive authentication failure; distinguish service unavailability from invalid credentials; provide retry through existing UI states. Test refresh, expiry, revocation, back navigation, and inconsistent storage. Do not automatically replay unfinished mutations.

### Verification and operations gaps

- S01 fixtures use in-memory SQLite and `Base.metadata.create_all`. Passing them does not prove PostgreSQL migrations, transactions, or restart persistence. CI now runs migrations against PostgreSQL, but the S01 auth fixture itself remains SQLite-based.
- The 26 backend/integration V cases and 12 browser B cases are not fully demonstrated. Missing coverage includes exact expiry boundaries, complete Origin/CSRF matrices, cross-session tokens, database failures, logs, browser lifecycle, and hosted Secure-cookie behavior.
- `session_secure_cookie` defaults to false. Local HTTP needs that exception, but the actual hosted Secure setting must be verified; the default alone does not prove a hosted defect.
- Admin provisioning accepts a password through a command-line argument and updates existing users without explicitly revoking their sessions. Prefer a hidden prompt/private input and define safe rerun behavior. The command was not exercised here.
- README still contains stale foundation statements that tables/migration revisions are absent. Existing planning statuses and historical reports must not be treated as a current execution ledger.

## Suggested order of work

1. Resolve the cookie/bearer contract and session rotation semantics; remove JavaScript-readable session credentials if retaining the approved cookie design.
2. Fix honest logout, sanitized validation errors, and expiry/service-failure recovery without redesigning portal layouts.
3. Expand S01 tests to assert state and confidentiality, then execute the contract against isolated PostgreSQL with migrations and failure injection.
4. Complete reproducible private role provisioning and update operating instructions in a separately authorized task.
5. Record desktop/mobile browser and hosted HTTPS login, refresh, direct links, role rejection, logout, expiry, outage/retry, and API restart evidence. Record actual cookie properties and old-credential denial.
