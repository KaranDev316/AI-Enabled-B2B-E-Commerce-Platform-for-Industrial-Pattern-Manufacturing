# S14 implementation review

Date: 22 November 2026. Reviewed revision: `ecc81b7`. User shorthand “s014” is interpreted as S14. Existing untracked S01–S06 reports were preserved. This task adds only this report; application files, configuration, dependencies, existing documentation, reference assets, and real uploaded files were not edited.

**Assessment: S14's basic support conversation works, but S14 should remain open.** Unified ticket creation, owner/Admin access, replies and status updates exist. Blank tickets, unsupported lifecycle states, attachment consistency/recovery defects, stale-update handling and incomplete persistent/browser evidence prevent acceptance.

## What S14 was supposed to deliver

Sources: [CONTEXT](../CONTEXT.md), [master PRP](../PRP.md), [PRP-009](../PRPs/009-support-and-complaints.md), [S14 slice specification](../VERTICAL_SLICE_PLAN.md#s14--resolve-a-customer-support-ticket), and [verification obligations](../VERIFICATION_PLAN.md#12-verification-obligations-for-remaining-slices).

Customer raises an inquiry or complaint, optionally linked to their own order. Admin reviews, replies and changes status. Customer adds context to the same conversation; Admin provides a resolution and marks it Resolved. Owner and Admin see the same complete history and final state.

- Unified owned tickets and multiple messages with author, role, time and chronological order.
- Optional related order must belong to the Customer. Another Customer and Employee cannot read/reply or access attachments by guessing IDs.
- Status is **Open, In Progress, or Resolved**. Stale conflicting updates and failed replies/status changes must not produce an incorrect success or fabricated result.
- Attachments accept JPG/JPEG/PNG/PDF, **at most two per submission**, 20 MB each, using shared private persistent storage, validation and failure-consistency rules.
- Loading, empty, invalid, denied and unavailable states remain distinct; failed input remains recoverable.
- No standalone chat, AI conversation, email, presence, support-assignment queue, internal notes, ticket export, separate inquiry entity, or employee-production-issue model.

S14 owns REQ-30/31/32 and AC-09-01 through AC-09-06. It depends on S01/S02 account access, S06 private-file safeguards, and actual owned-order validation. Earlier defects in those dependencies remain relevant.

## What is good

1. Inquiry and complaint share one ticket/message model. Later correspondence stays attached to the same record instead of creating an unrelated chat.
2. Owner and role checks protect ticket detail, replies and files. Tests deny another Customer and Employee from conversations, and deny another Customer's attachment download.
3. Ticket ownership is server-controlled. Related orders and the additional RFQ association are checked against the same Customer before creation; the own-order and foreign-order paths are tested.
4. Initial message and ticket use one commit. Replies preserve sender ID/role and time; an Admin reply advances an open ticket to in progress in the same transaction.
5. Messages are persisted before the UI reloads them; ordinary failed message requests are not appended optimistically as if saved. Resolved replies are rejected server-side.
6. File responses use authorized application routes rather than public bucket URLs. Support's extension allowlist correctly excludes CAD/WEBP/DXF.
7. UI reuses existing Customer/Admin layouts and protected-file components. Current creation feedback distinguishes HTTP attachment failures from a saved ticket, although network failures and reply attachments need correction.

## What is wrong or incomplete

### Medium — whitespace-only tickets are saved

Create schemas validate length before the service strips subject/message and have no normalized blank check. An isolated current service probe created a ticket whose subject and initial message both became empty strings. Frontend create validation rejects blank input, but direct API callers bypass it. Frontend also requires five message characters while backend requires three, producing inconsistent feedback.

**Suggestion:** normalize ordinary text before enforcing useful required lengths, align client/server rules, and test exact boundaries and no partial ticket/message rows after rejection. Do not normalize passwords or silently alter meaningful message text beyond agreed whitespace handling.

### Medium — lifecycle and request taxonomy depart from approved scope

Model/schema/routes and both portals support a fourth **Closed** state. A direct service probe confirmed Closed is accepted. PRP-009 explicitly normalizes the workflow to three states. Existing tests currently assert the extra state, so green tests reinforce the departure rather than demonstrate compliance.

UI/model also expose `order_issue` and `technical_support` as additional ticket types. The approved request types are inquiry/complaint; these extra classifications and RFQ linking should be reconciled with the requirement owner rather than treated as required because they exist.

**Suggestion:** align the lifecycle with Open/In Progress/Resolved, safely account for any existing Closed records, and clarify classification/association scope. Preserve records and current portal shells; do not remove persisted history as a shortcut.

### Medium — status changes have no stale-conflict protection or resolution-response association

`update_status` directly assigns any enum state without an expected version/current-state check or recorded status event. Competing Admin updates can overwrite each other. `add_message` checks status before committing without serializing against resolution, so a reply can race with a resolve action. REQ-32 explicitly requires stale conflicting updates to fail honestly.

A probe also resolved a ticket containing only its Customer initial message; no Admin resolution response was required. The PRP's intended journey includes a visible resolution response. Whether a separate required resolution message is mandatory should be made explicit; merely changing a badge does not demonstrate the complete journey.

**Suggestion:** establish authoritative transitions and conflict detection, record meaningful update evidence, and verify response-then-resolution behavior. Test two Admins and reply-versus-resolution in PostgreSQL. No concurrent race was executed here.

### High — customer reply attachment failures are ignored

`handleSendTicketReply` commits the message first, then uploads the selected file without checking the upload response. HTTP 400/403/500 therefore clears the selected attachment and reply and reloads the conversation without informing the Customer that the file failed. A network exception instead leaves an already-saved message with generic failure and potential repeat-message retry.

Ticket creation checks non-OK upload responses, but an upload network exception exits its outer handler after the ticket was committed, without the normal “ticket created, attachment failed” reconciliation. Retrying creation can create another ticket.

**Suggestion:** distinguish saved ticket/message from failed attachment, check every response, preserve failed file selection/retry context, and recover against the saved ID. Test storage failure, HTTP error, network/response loss, and successful retry. This is source-confirmed; browser failure injection was not performed.

### High — attachment writes lack storage/database compensation

`SupportService.attach_file` saves bytes, inserts metadata and commits without rollback/object cleanup around metadata failure. An isolated current probe injected database commit failure after a fake storage write: **one new orphan object remained and no new attachment metadata persisted**. Partial storage-write exceptions likewise have no attempted-key compensation.

**Suggestion:** compensate attempted objects for storage/metadata failures, sanitize diagnostics, and make failed cleanup observable/reconcilable. Test failures on first/second file, after storage success, at commit and during cleanup. S04's catalogue safeguards do not automatically protect this separate service.

### Medium — file count rule is incorrectly enforced across the whole ticket

`attach_file` counts all ticket attachments and rejects the third attachment forever. The requirement is two files **per submission**, unlike S06's explicit two files total per RFQ. A legitimate later reply cannot attach more evidence after two earlier attachments. Files are linked only to the ticket, with no message/submission association to express or enforce the actual rule.

The count is also not transactionally serialized. If a total cap were intended, concurrent uploads could exceed it; the current sequential test does not establish concurrency safety.

**Suggestion:** represent and enforce the approved per-submission grouping, including reply attachments and concurrent requests. Do not blindly copy the RFQ-wide two-file cap into support.

### Medium — shared private-file requirements remain incomplete

- The file is read fully before the 20 MiB check; there is no bounded/streamed read.
- Shared content checks accept truncated PNG and superficial PDF headers, as established by the S06 review. S14's PNG success fixture is truncated and does not prove a usable image preview.
- Shared storage silently falls back to ephemeral local disk when remote configuration is absent. That cannot close required private Supabase persistence.
- `retrieve_file` does not normalize storage exceptions, so missing objects/outages can become server errors rather than a clear missing/unavailable outcome.
- Uploads remain allowed on Resolved tickets while replies are rejected. A probe successfully attached a malformed-signature PNG to a Resolved ticket. This is inconsistent lifecycle behavior requiring a defined rule and test.
- Filenames are interpolated into download headers; shared sanitization leaves control characters. Verify safe Unicode/control-character handling. No header-injection reproduction was performed.
- Byte responses omit an explicit nosniff header, unlike RFQ/catalogue file routes. Global middleware supplies no-store, so the route's narrower cache header alone is not evidence that responses are cached.

**Suggestion:** resolve shared S06 validation/persistence defects, then apply and test the support-specific allowlist and lifecycle behavior without introducing CAD or a public bucket.

### Medium — Admin queue failures can masquerade as empty or stale data

`fetchAdminTickets` ignores non-OK responses and only logs network exceptions. It finishes loading without a visible error, leaving an empty queue or old rows. Customer lists have a dedicated error state, but related-order/RFQ context loading silently fails. Open conversation objects are not refreshed by list polling; another participant's replies/status can stay invisible until reopen or own action.

**Suggestion:** distinguish unavailable queue/context from empty data, expose retry, and refresh selected conversations at appropriate points. Real-time messaging infrastructure is unnecessary; ordinary refresh/reopen must be truthful. Preserve unsent reply text during retrieval failures.

### Reliability gap — ticket reference allocation is not concurrent-safe

`generate_ticket_number` uses yearly ticket count plus one. Concurrent requests can choose the same number; the unique constraint rejects one, but creation lacks handled allocation retry/conflict behavior. Count-based allocation also assumes retained numbering has no gaps from deletion/import.

**Suggestion:** use atomic allocation or controlled collision retries and verify parallel submissions against PostgreSQL. Lost-response creation/reply retry semantics also need a defined recovery path; identical intentional messages must not be automatically merged without a rule.

## Reference alignment

Opened the actual Customer support page, Admin queue and redesigned Admin conversation references. The Customer implementation keeps a create/list arrangement and the existing Customer shell, but conversation opens in a modal rather than the reference's inline detail. Admin uses queue/table plus modal instead of the preferred list/conversation split. Source retains the portal colors and roles; rendered spacing, focus and mobile overflow were not measured.

Supported adaptations are the 20 MB limit instead of the mockup's 10 MB, Open/In Progress/Resolved terminology, persisted records rather than sample names/counts, and omission of unsupported assignment/export/internal-note/notification controls. Extra Closed status is not a supported adaptation. Keep UI improvements focused within established components; this review authorizes no redesign.

## Suggested order of work

1. Fix attachment failure reporting/compensation and blank input validation.
2. Reconcile the three-state lifecycle and enforce stale-update/reply-resolution consistency.
3. Correct per-submission attachment grouping and apply shared safe file handling/persistence.
4. Make unavailable queue/context and selected-conversation refresh honest and recoverable.
5. Expand tests against the AC IDs: all roles/actions, real own/foreign orders, file-parent mismatch, exact boundaries, storage/database failures, lost responses and concurrent updates/reference allocation.
6. Demonstrate the full Customer → Admin → Customer → Admin resolution journey at desktop/mobile sizes, with keyboard/focus/error/retry checks, then real private storage, PostgreSQL migrations/restart and hosted session checks.
