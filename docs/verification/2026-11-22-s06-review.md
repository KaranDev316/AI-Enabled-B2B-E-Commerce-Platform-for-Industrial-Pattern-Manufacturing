# S06 implementation review

Date: 22 November 2026. Reviewed revision: `ecc81b7`. Existing untracked S01–S05 reports were preserved. This task adds only this report; no application, configuration, dependency, existing documentation, reference assets, or real uploaded files were changed.

**Assessment: S06 is partially implemented and should remain open.** RFQ upload/list/download/removal and authenticated preview UI exist, with useful basic ownership tests. Required profile-image support is missing; concurrent file limits, content integrity, private persistence, and failure compensation are incomplete. Passing current tests does not close these requirements.

## What S06 was supposed to deliver

Sources: [CONTEXT §7](../CONTEXT.md#7-files-and-ml-boundaries), [PRP-003](../PRPs/003-rfqs-and-files.md), [PRP-001](../PRPs/001-accounts-and-access.md), [S06 slice scope](../VERTICAL_SLICE_PLAN.md#s06--attach-drawings-and-retrieve-authorized-files), and [verification obligations](../VERIFICATION_PLAN.md#12-verification-obligations-for-remaining-slices).

Customer selects permitted attachments in the RFQ wizard, reviews/removes them before submission, and submits. Owner/Admin can retrieve the correct files, preview images/PDFs, and download CAD. Users can also save a permitted own-profile image through the same validated storage foundation.

- Maximum **two files total per RFQ**, including concurrent submissions; each at most 20 MB with a consistent byte convention.
- RFQ allowlist: JPG/JPEG, PNG, PDF, STEP/STP, IGES/IGS, STL, DWG. Profile images: JPG/JPEG/PNG only.
- Streamed byte limits and appropriate backend content validation; browser filename/MIME alone cannot establish type. No CAD manufacturing analysis or interactive CAD viewer.
- Private Supabase objects, PostgreSQL metadata, generated storage keys, original filename metadata, authorization before retrieval, no public customer-document URLs.
- Storage/database failures must not leave falsely successful broken associations or intentionally abandoned objects. Files must survive application restart.
- Profile image changes preserve ownership. Assigned Employee access is explicitly completed in S10; denying unassigned Employees is required now.

S06 covers attachment portions of REQ-08, REQ-09 except assigned-Employee integration, profile-image portions of REQ-03, and AC-03-04/05/06/07. It inherits S01 sessions and S05 RFQ ownership/recovery requirements.

## What is good

1. File permissions follow the RFQ owner and server role. A second Customer cannot list/download/upload/delete another Customer's attachments in the tested cases. File ID is checked against the requested parent RFQ.
2. Unauthenticated reads are blocked; mutations use Origin/CSRF. Owner changes are restricted to submitted status rather than allowing silent edits after review.
3. Keys are generated separately from original filenames, and metadata responses expose authorized route IDs rather than private storage paths or credentials.
4. Downloads return nosniff and private/no-store headers with explicit MIME/length/disposition. Basic tests verify returned bytes rather than status alone.
5. The frontend file helper explicitly supplies the current tab credential with cookies omitted and rejects unsupported external addresses/redirects. Two focused frontend tests pass.
6. Preview rendering uses fetched blobs, restricts active preview types, offers retry, and revokes object URLs. CAD is not treated as a manufactured/validated model or interactive viewer.
7. Failed post-create uploads are reported as “RFQ saved, files failed” with retry guidance. Selected-file removal before submit operates on local state and does not create a premature persisted attachment.

## What is wrong or missing

### High — required profile-image workflow is absent

S06 explicitly completes profile images deferred from S02. Searches of backend routes/schemas/models/migrations and frontend components found no persisted profile-image association or upload/retrieval flow. The profile route edits text only; Employee avatar uses initials and Customer profile uses a generic company icon.

**Suggestion:** implement owner-scoped JPG/JPEG/PNG profile images, migration/metadata, safe replacement/cleanup, private persistence, and UI controls inside the approved profile layout. Verify another user cannot replace/read images outside the intended permission model. Do not interpret decorative avatar styling as completed upload support.

### High — the two-file limit is not concurrency-safe

`attach_rfq_file` reads the RFQ and counts existing files, then performs storage writes and inserts metadata. It does not lock the parent or serialize competing attachments. With one file already present, two concurrent transactions can both observe one and both add a file, exceeding two. Status changes can also race with upload/removal because editability is checked before these unprotected operations.

The existing test mentioning AC-03-05 uploads sequentially and checks a third request; it does not execute concurrent requests.

**Suggestion:** serialize parent-scoped count/status checks and metadata changes with a consistent transaction/locking strategy. Prove competing upload/upload and upload/review/delete behavior against independent PostgreSQL transactions. No concurrency reproduction was run here; the missing guard is source-confirmed.

### High — content validation accepts malformed files and unsupported extra formats

Direct current validator probes accepted an eight-byte PNG signature with no image, `%PDF-fake`, a one-character IGES file containing `G`, and 84 arbitrary bytes as STL. The existing PNG success fixture is itself truncated after its initial header, so that green test does not prove a browser-decodable image. Some PDF fixtures likewise contain only superficial header/trailer text.

Checks are too shallow: PNG/JPEG/PDF rely on prefixes, IGES accepts any occurrence of a section letter, and binary STL accepts any length of at least 84 bytes without verifying triangle-count consistency. The allowlist and frontend also enable WEBP and DXF, which CONTEXT excludes from RFQ formats.

**Suggestion:** enforce the exact approved allowlist; validate images with real decoding/integrity checks and PDFs with appropriate structural checks. Validate CAD structure sufficiently to reject obvious non-files without manufacturing analysis. Replace success fixtures with actual valid files and test damaged/truncated/type-mismatched inputs. A fabricated file being accepted is not evidence of malware execution; no such execution is claimed.

### High — partial storage writes leave orphaned objects and expose internal errors

The upload handler calls `save_file` before metadata creation. If storage writes bytes and then raises, its exception path returns immediately without deleting the attempted key. A current isolated service probe simulated this: **HTTPException 500; one orphan object remained; a synthetic internal error marker appeared in response detail**.

The response embeds `str(exc)`. The shared storage service also logs and raises raw remote response text on upload failure. This can disclose internal storage diagnostics; no real credential leak was attempted or established.

Metadata-commit failures attempt object deletion, but the shared delete method suppresses errors/ignores HTTP failure statuses, so cleanup is not reliably established.

**Suggestion:** track attempted keys before writing, compensate partial outcomes, sanitize errors/logs, and make cleanup failures observable with a reconciliation procedure. S04 has stronger catalogue-specific compensation/error handling worth adapting within existing services; it does not automatically protect RFQ files.

### High — deletion can destroy bytes before metadata commit succeeds

`delete_rfq_file` deletes storage bytes first, then deletes metadata and commits. A successful object deletion followed by database failure leaves a saved association pointing to missing content. Conversely, remote HTTP deletion failures are not checked and can be followed by successful metadata removal, abandoning bytes.

**Suggestion:** coordinate association removal and object cleanup with explicit retry/reconciliation semantics. Test both database failure after object deletion and remote deletion failure. This defect is source-confirmed; destructive real-storage failure tests were not performed.

### Medium — unconfigured uploads silently use temporary local storage

`StorageService` creates/writes a local `.private_storage` directory when Supabase is not configured. RFQ uploads do not refuse that fallback. A hosted upload can therefore report success while depending on ephemeral application disk, contrary to S06's private persistent storage boundary.

**Suggestion:** fail clearly when required private storage is unavailable, or explicitly confine any local adapter to isolated development/tests. Verify production/demo configuration and restart persistence using real private storage; no actual host misconfiguration is asserted here.

### Medium — size enforcement happens after full file read

The async upload endpoint uses `await file.read()` with no bound; the service checks size only after the bytes are loaded. This does not meet CONTEXT's streamed byte-limit rule and permits a much larger upload to be read before rejection.

**Suggestion:** read no more than the maximum plus one byte, or count chunks with early rejection. Apply ingress/request limits as appropriate and test at exactly **20 × 1024 × 1024 bytes**, one byte over, and oversized streams. Current tests reject a file over the limit but do not prove bounded reading or exact-boundary acceptance.

### Medium — download errors are all reported as missing content

`get_rfq_file_data` catches any storage exception and returns 404 with its raw exception string, including storage outages. The underlying reader can classify upstream non-200 failures as FileNotFoundError. Users cannot distinguish a missing object from a temporarily unavailable service, and internal key/path details can enter responses.

**Suggestion:** return sanitized, distinct not-found/unavailable outcomes and preserve retry. Test missing object, permission/configuration failure, timeout and upstream 5xx with the RFQ itself still readable.

### Recovery and UI limitations

- After creating an RFQ, uploads are separate requests; Admin may mark it under review before all uploads finish. Failed attachments then cannot be retried through the submitted-only endpoint. Define this race/recovery behavior without inventing a saved-draft product feature.
- Selected files are cleared after the partial-success path. Guidance names failed files but users must reselect them. Verify this is understandable and recoverable, especially with two-file counts and a lost upload response.
- The hidden `d-none` file input is activated through a styled label rather than a normal keyboard-focusable button. Keyboard operation of Browse and nested preview dialogs requires testing; no accessibility pass is claimed.
- `sanitize_filename` leaves CR/LF control characters, while download routes interpolate the name into Content-Disposition. Validate/safely encode header filenames and test control characters, quotes, Unicode, long names and path separators. No header-injection reproduction was performed.
- S01's JavaScript-readable session credential and stale-auth recovery findings remain inherited dependencies despite the improvements in file-specific credential selection.

## Suggested order of work

1. Fix file count/status concurrency, safe storage compensation/deletion, and sanitized errors.
2. Enforce private persistent storage and bounded reads; tighten the exact allowlist and real content validation.
3. Implement the missing profile-image workflow in existing profile components.
4. Expand S06 tests with valid fixtures, independent PostgreSQL transactions, failure injection, exact limits, all supported formats, crossed parent/file IDs and full authorization/Origin/CSRF matrices.
5. Exercise wizard partial success, lost response, concurrent Admin review, retry/removal, image/PDF preview and CAD download at desktop/mobile sizes. Verify file controls and dialogs by keyboard.
6. Run real private Supabase roundtrips, migration/retained-record checks and API restart persistence. Record unexpired/revoked file-session behavior and hosted acceptance separately.
