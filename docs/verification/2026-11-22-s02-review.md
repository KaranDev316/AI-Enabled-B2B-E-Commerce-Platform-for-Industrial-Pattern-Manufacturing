# S02 implementation review

Date: 22 November 2026. Reviewed revision: `ecc81b7`. The existing untracked S01 report was preserved. This task adds only this report; no application, configuration, dependency, design, or existing documentation files were edited.

**Assessment: S02 is substantially present but incomplete and should remain open.** Registration, Customer/Employee profile editing, employee creation, status management, reset, and self-password change exist. Mandatory password change is bypassable, invalid account/profile data is accepted, validation responses expose password input, and Admin profile self-service is incomplete. Green tests do not establish acceptance.

## What S02 was supposed to deliver

Sources: [CONTEXT](../CONTEXT.md), [master PRP](../PRP.md), [PRP-001](../PRPs/001-accounts-and-access.md), [S02 slice scope](../VERTICAL_SLICE_PLAN.md#s02--register-maintain-profiles-and-manage-account-access), and [verification obligations](../VERIFICATION_PLAN.md#12-verification-obligations-for-remaining-slices).

The intended journey is: a visitor registers a Customer account and owned business profile together, signs in, and maintains permitted details. Admin creates an Employee who can sign in and maintain personal details. Admin activates/deactivates customer/employee accounts and resets passwords. Reset revokes previous sessions and requires password change before normal work resumes. Successful self-password change revokes existing sessions and requires fresh login.

Required boundaries:

- Public registration always creates Customer accounts, with one business profile per login; submitted roles cannot grant privilege.
- Customer, Employee, and Admin can maintain their permitted own profile/password under REQ-03. Role, activation, another user's details, and Employee employment facts cannot be changed through self-service.
- Invalid inputs produce useful field feedback and preserve existing state. Failed or duplicate account creation leaves no incomplete user/profile pair.
- Deactivation/reset/password change invalidate affected sessions while preserving account identity and operational links.
- Backend authorization, trusted-Origin checks, session-bound CSRF, and safe errors apply to direct requests as well as UI controls.
- Profile images belong to S06. Invitations, email reset delivery/verification, configurable roles, suppliers, and two-factor authentication are excluded.

S02 owns REQ-01, REQ-03, REQ-04; AC-01-01/02/06/07/08; and the reset/deactivation portion of AC-01-04. REQ-03 images complete in S06. S01 session defects remain dependencies, not new S02 features.

## What is good

1. Registration and employee creation assign roles on the server and reject extra request fields. Public callers cannot select Admin/Employee through the registration schema.
2. User/profile creation uses one commit after the user flush, providing the correct transactional foundation. Failure-injection evidence is still needed to prove rollback behavior.
3. Passwords use Argon2id. Reset, deactivation, and self-password change delete session records while retaining the same user identity.
4. Own-profile targeting comes from authenticated identity. Employee department changes are ignored by the service, preserving employment facts.
5. Admin routes enforce backend role guards. Protected writes include Origin/CSRF checks; hiding buttons is not the only protection.
6. Current Customer/Employee profile components use honest empty values such as “Not provided” and “Not assigned.” Earlier findings about invented address/department fallbacks do not apply to those current components.
7. Admin now has an explicit Change password action in the account menu. This is a concrete improvement since the earlier S02 review.

## What is wrong

### High — reset users can bypass mandatory password change

The current isolated HTTP sequence reset a Customer's password, confirmed the old session returned **401**, signed in with the reset password, and received `must_change_password=true`. Before changing it, the client updated its company name: **200**, and a subsequent GET confirmed persistence.

`get_current_user`, role guards, and `ProtectedRoute` do not enforce the flag. Portal warnings and a dismissible modal do not prevent direct requests or normal work. The existing reset test checks revocation and the flag but stops before testing restricted access. This fails AC-01-08.

**Suggestion:** enforce restricted temporary-password access on the backend, allowing only necessary identity/password-change/logout operations. Route flagged users into the existing password-change flow and test direct normal requests, completion, fresh login, and no automatic replay of earlier mutations.

### Medium — required registration and employee values become empty after validation

A registration containing spaces for company/contact/phone returned **201**, storing all three as empty strings. Admin employee creation with a space-only name also returned **201**, storing an empty full name.

Schema length checks happen before service trimming, so these values pass validation and become invalid records. This violates AC-01-02 and employee-account integrity expectations.

**Suggestion:** trim ordinary text before checking required lengths, reject normalized blanks, and test minimum/maximum boundaries. Do not trim or normalize passwords.

### Medium — profile updates bypass bounded schemas

The profile route uses `ProfileUpdateRequest`, whose optional strings have no bounds, rather than the bounded Customer/Employee schemas. A current SQLite HTTP probe accepted a **256-character company name and one-character phone**, returning **200** and storing both.

SQLite does not enforce PostgreSQL `VARCHAR` lengths. This demonstrates missing API validation, not a new PostgreSQL execution result. On PostgreSQL, overlong values can instead become database errors. Required blank edits are also ignored with success rather than useful validation feedback. Missing profiles are silently created with empty required fields in the service.

**Suggestion:** validate role-appropriate fields and normalized lengths at the API boundary, reject unsupported/privileged fields explicitly, and preserve the full previous record on invalid saves. Treat unexpectedly missing required profiles as an integrity condition rather than manufacturing empty ones.

### Medium — Admin profile updates report success without applying details

An authenticated Admin submitted full name and phone to `/api/profile/me`: **200**, but the response did not contain the submitted name. `update_own_profile` has only Customer and Employee branches and commits successfully for Admin without applying those fields.

REQ-03 includes Admin, so this is incomplete self-service. The Admin password-change entry is now present and should not be conflated with the remaining profile gap.

**Suggestion:** define the permitted Admin profile fields explicitly and implement persistence through the established account UI. Reject unsupported updates instead of returning misleading success; do not invent an employment profile or redesign portal navigation.

### High — S02 validation responses expose submitted password input

A direct invalid registration using a synthetic marker inside a password array returned **422** and included that marker in its response. This confirms the shared default-validation confidentiality defect on an S02 endpoint, independently of the S01 login probe.

Default validation errors also use a list, while forms generally expect `detail.message`; users consequently receive generic failure text rather than useful field feedback.

**Suggestion:** introduce normalized, sanitized validation responses, omit secret input values from responses/logs, and test registration/reset/change-password error paths. No real password was printed or included in evidence.

### Lower priority — account displays and feedback need tightening

- `list_users` labels all stored session rows as `active_sessions_count` without filtering expiry. Expired rows not yet resolved can inflate the displayed count. Source-confirmed query behavior; no browser reproduction performed.
- Employee department and other irrelevant profile fields can receive success while being ignored. Privilege is preserved, but feedback should clearly reject unsupported edits.
- Admin user table fallbacks such as “Production” for absent Employee department can still present an assumed employment fact. Use an honest missing-value label consistent with the corrected Employee profile.
- The password modal lacks explicit label/input associations and dialog accessibility semantics in source. Keyboard focus, focus return, and accessible naming need browser verification; no accessibility pass is claimed.

## Suggestions and remaining verification

1. Fix backend forced-change enforcement and secret-safe validation first.
2. Normalize and bound role-specific profile/account inputs; reject blanks and unsupported fields; complete Admin profile self-service.
3. Add meaningful checks for exact user/profile counts, failure rollback, duplicate races, invalid-save preservation, and revoked/temporary credential behavior. A uniqueness constraint alone does not guarantee useful conflict feedback; no handled concurrent `IntegrityError` path was established in the account service.
4. Execute against isolated PostgreSQL with actual migrations. Include concurrent reset/password-change/login/deactivation, ensuring old-password sessions cannot survive a completed invalidation race. These races were not executed here.
5. Verify every Admin action as anonymous, Customer, Employee, and Admin; exercise full Origin/CSRF rejection matrices and assert unchanged data after rejection.
6. Run desktop/mobile browser journeys for registration, profile save/reload, Admin creation/status/reset, forced password change, all-role password change, loading/errors/retry, keyboard use, and open-tab session invalidation. Reuse the approved layouts and references.
7. Check hosted HTTPS, retained account/operational links, restart persistence, and safe logs; record current-revision results. Migration startup and repeat-startup checks now exist in CI, unlike the older report's configuration; no current CI execution is claimed here.

Session transport, misleading logout, and stale auth recovery described in [the current S01 report](2026-11-22-s01-review.md) also affect S02. Fixing S02 flags alone will not complete browser session behavior.
