# S05 implementation review

Date: 22 November 2026. Reviewed revision: `ecc81b7`. Existing untracked S01–S04 reports were preserved. This task adds only this report; no application, configuration, dependency, existing documentation, or reference files were edited.

**Assessment: S05's main RFQ workflow exists, but should remain open.** Standard/custom submission, owner/Admin inspection, identifiers, persisted status, and basic isolation work in local tests. Incomplete review, weak validation, unsupported status changes, submission recovery, and missing browser/PostgreSQL evidence prevent acceptance.

## What S05 was supposed to deliver

Sources: [CONTEXT](../CONTEXT.md), [master PRP](../PRP.md), [PRP-003](../PRPs/003-rfqs-and-files.md), [S05 slice scope](../VERTICAL_SLICE_PLAN.md#s05--submit-and-inspect-an-rfq-without-attachments), and [verification obligations](../VERIFICATION_PLAN.md#12-verification-obligations-for-remaining-slices).

Customer chooses an existing active product or custom requirement, enters manufacturing details, reviews a three-step wizard, edits without losing input, and submits an owned RFQ. Admin and owner inspect the same saved requirements and status. Another Customer and an unassigned Employee cannot read it.

- Step 1 captures product/custom requirement, material, quantity and description.
- Step 2 captures dimensions, specifications and notes. Attachments are optional; upload functionality belongs to S06.
- Step 3 reviews the entered details and reused business contact information before submission.
- Valid submission without files succeeds and returns an identifier/status. Invalid input identifies relevant fields. Failed submission retains recoverable input and cannot claim a nonexistent saved request.
- Status reflects persisted actions. Available quotation status integrates in S07; no quotation, order or invoice is fabricated by S05.

S05 covers REQ-08 excluding attachment interaction, REQ-10's initial saved-request inspection, and AC-03-01/02/03/08. File validation/concurrency/preview belongs to S06; assigned Employee access belongs to S10. Later integrated features are not automatically S05 acceptance evidence.

## What is good

1. Ownership comes from authenticated identity rather than submitted customer ID. Customer lists are owner-filtered; direct detail checks deny other Customers and Employees.
2. Standard RFQs require a real active product on the backend. Custom RFQs work without product linkage, preserving the intended alternative flow.
3. Newly created requests have a server-generated reference and submitted status. Creation does not generate a quotation, price, invoice, or order.
4. Wizard state is collected once and reused. Back buttons change the step without resetting values; a failed create request leaves form state intact.
5. The submit button is disabled while pending, and the handler checks the current step and pending state. This reduces ordinary double clicks, although it does not solve lost-response retries.
6. Admin receives persisted requirements plus owner context and can mark a submitted request under review. Customer views have visible request references/statuses.
7. Current attachment integration reports that an RFQ was saved when later attachment upload fails, rather than pretending the entire request disappeared. That is an honest distinction; deeper S06 consistency remains separate.

## What is wrong or incomplete

### Medium — final review omits description and notes

Step 3 shows title, type, material, quantity, dimensions, target date, specifications, attachments and brief contact details, but does not show `rfqForm.description` or `rfqForm.notes`. Both values are collected and submitted. Email is also absent from the contact summary.

This leaves the Customer unable to review all entered manufacturing details before submission and does not meet the complete-review intent of REQ-08/AC-03-02. The supplied review reference explicitly presents description and additional requirements/notes.

**Suggestion:** include every submitted manufacturing field and relevant reused contact detail once, with clear edit navigation. Preserve the current wizard and shell; do not add duplicate inputs or a separate draft feature.

### Medium — input validation is inconsistent and incomplete

An isolated current HTTP probe submitted title `" x "`, material `" y "`, no description/dimensions, and target date `"not-a-date"`. It returned **201**, storing one-character title/material and the arbitrary date string. Length constraints run before the after-validator trims, so padded one-character values bypass declared minimum lengths. Blank-only title/material are correctly rejected.

Description/dimensions are optional in the schema and UI. The approved flow requires useful manufacturing input and the references mark description/dimensions required, but the written PRP does not define precise conditional minimums. Do not invent numerical manufacturing limits from mockup examples. Define the intended required fields for each supported flow before closing AC-03-03; the current tests prove only quantity, blank title and missing standard product rejection.

The frontend advances from step 1 using a `type="button"` and selected manual checks, bypassing full native form validation. Backend validation errors are generally reduced to generic “RFQ submission failed,” without field feedback.

**Suggestion:** normalize text before length validation, validate supplied dates as dates, define required manufacturing fields explicitly, and map safe backend field errors to the relevant step. Verify invalid saves leave no RFQ row and preserve user input. Do not impose an unsupported future-date rule.

### Medium — material selector cannot represent all persisted catalogue materials

Selecting a product assigns its arbitrary `material_type` into form state, but the material dropdown contains six hardcoded choices. A persisted value such as “Cast Iron Grade 20” from the existing standard-product fixture has no matching option. The control can show no selected option while review/submission still use the unmatched state value.

**Suggestion:** support the selected product's actual material and appropriate custom input through the established control. Do not silently replace persisted material with a default. Test catalogue values outside the hardcoded list.

### High — Admin can claim quoted status without a quotation

`RFQStatusUpdateRequest` accepts every enum value; `update_rfq_status` assigns it without transition or business-record checks. In an isolated HTTP sequence, a newly submitted RFQ with no quotation was changed directly to **quoted**, returning **200**.

The UI currently offers only submitted → under_review, but direct requests bypass that limitation. REQ-10 requires Customers to distinguish a submitted request from an available quotation; a manually assigned quoted label is not proof that an offer exists. It can also move terminal states backwards because the service has no transition guard.

**Suggestion:** limit this endpoint to permitted review transitions. Let actual quotation/lifecycle operations set their associated states, enforce action-time checks on the backend, and test direct forbidden transitions. This concerns the S05 status surface and S07 integration, not permission to redesign the quotation workflow.

### Reliability risk — concurrent requests can choose the same RFQ number

`generate_rfq_number` reads the latest matching record and adds one. There is no sequence allocation/serialization or conflict-retry handling around creation. Two concurrent transactions can choose the same reference; the unique database constraint prevents duplicate references but one request can fail with an uncontrolled database exception.

**Suggestion:** allocate references atomically or handle collisions with a bounded transactional retry. Prove behavior with independent PostgreSQL transactions. This is source-derived; no concurrency race was executed in this review.

### Reliability gap — ambiguous response loss can create duplicate requests

An isolated probe sent the same valid creation payload twice and received **201** twice with different RFQ IDs. Separate intentional similar requests may be valid; S05 does not explicitly prescribe payment-style idempotency. However, if the first commit succeeds and its response is lost, the current error/retry flow cannot reconcile that outcome and a retry creates another request.

**Suggestion:** define recoverable submission semantics, such as a request-attempt identifier or an explicit reconciliation step before retry. Test commit-success/response-loss, reload, and retry. Do not present this as a demonstrated ordinary double-click defect or a requirement to merge all identical business requests.

### Other findings and evidence gaps

- `fetchCatalogueProducts` silently ignores non-OK responses and logs network errors without a usable catalogue-load state. Standard selection can look empty when its dependency is unavailable. Provide loading/error/retry while retaining custom form input.
- Customer/Admin detail fallbacks say “As per CAD drawing” and “Standard delivery” when no dimension/date exists, even for requests without files. Use “Not specified” rather than implying a drawing or agreed schedule.
- RFQ contact facts are derived from the current profile, not snapshotted. A probe changed profile contact after submission and Admin detail immediately showed the new contact. The requirements do not explicitly demand immutable RFQ contact snapshots; clarify whether details represent current contact or submitted contact, label accordingly, and test Customer/Admin consistency.
- Open detail dialogs store objects separately from refreshed lists, so background changes can leave stale detail status. Verify refresh/reopen and state recovery rather than assuming polling keeps every surface current.
- Admin list filters accept arbitrary strings and can turn invalid status/type values into an empty result rather than actionable validation. Invalid-query and outage/empty distinctions need coverage.
- S01 stale-auth/logout and S02 forced-password-change defects apply to RFQ creation too. Existing session dependencies do not close those findings.

## Reference alignment

Inspected the actual three Customer wizard references and Admin RFQ/quotation reference, using the global UI kit already inspected in this review series.

The current Customer flow retains the existing sidebar, three-step order, orange/navy identity and primary submission controls. It uses simpler radio choices and a compact review instead of the reference's request cards and grouped review panels. The Admin implementation uses a wide table and modal inspection rather than the reference's table/detail split. These are source/reference differences; rendered proportions and mobile behavior were not measured.

Intentional functional adaptations supported by requirements include standard/custom terminology, reuse of profile facts, no invented customer data, a two-file/20 MB limit rather than the old mockup limit, and exclusion of notifications/email promises/AI chat/CAD previews. A single dimensions string and combined technical specification field reflect the current backend contract; they must still be reviewed accurately. Those adaptations do not justify omitting description/notes or replacing the approved layout hierarchy.

**Suggestion:** correct review completeness within existing components first, then compare desktop/mobile rendering against the actual references before deciding whether further focused alignment is needed. Preserve approved routes and shells.

## Suggested order of work

1. Guard backend review transitions and complete the final review summary.
2. Correct trimmed validation, supplied dates, material selection, and useful per-field feedback; settle required-input semantics under the approved requirements.
3. Make catalogue dependency failures and missing values honest and recoverable.
4. Test and correct concurrent numbering and ambiguous submission recovery without adding a saved-draft product feature.
5. Run isolated PostgreSQL tests for creation rollback, deactivation-versus-standard-selection, concurrent submissions and persisted owner/product relationships. Verify current contact semantics and real quotation integration.
6. Run desktop/mobile standard/custom wizard journeys, back/edit, invalid input, service outage/retry, successful no-file submit, owner/Admin reload/inspection, unauthorized navigation and revoked session recovery. Record hosted and restart results separately.
