## What S07 was supposed to implement

Sources: [approved context](../CONTEXT.md), [S07 slice plan](../VERTICAL_SLICE_PLAN.md#s07--issue-revise-and-respond-to-a-manual-quotation), [PRP-005](../PRPs/005-quotations-and-decisions.md), [PRP-004 manual fallback](../PRPs/004-ai-price-and-lead-time.md), [verification plan](../VERIFICATION_PLAN.md), and [existing S07 contract and evidence](../S07_VERIFICATION.md).

Admin reviews a persisted RFQ, prepares an itemized manual offer, saves and issues it. Its owning Customer can review the official values, reject it or request changes. Admin prepares traceable revisions without changing historical values.

- Persist RFQ-linked quotation versions, line items and customer decisions. Store item descriptions, quantities, unit prices, subtotal, sample tax rate/amount, total, lead time, optional validity and pricing provenance.
- Use INR Decimal calculations, server-derived totals and an explicit sample-tax label.
- Increment versions within each RFQ. Creating a newer draft immediately supersedes the preceding unaccepted version; no duplicate versions or two current offers under concurrent work.
- Preserve prior versions. Accepted offers cannot be edited or superseded.
- Keep incomplete drafts unissuable and unpublished draft prices private. Only the owning Customer can review issued offers and respond to the current, sent, unexpired version.
- Save rejection/change requests for Admin without changing official prices. A change request does not introduce a new quotation status.
- Manual pricing must work without model artifacts, with `pricing_source=manual` and null estimate reference. No AI training, confidence percentage or external message delivery belongs to S07.

S07 owns REQ-14/15/16 and manual/provenance portions of REQ-13; AC-05-01 through AC-05-05 as applicable to preparation/review. Acceptance/order/invoice creation belongs to S08; full missing/corrupt model evidence belongs to S15. Acceptance now exists in this checkout because S08 is also implemented. Its presence is not an S07 scope defect, although the older S07 statement that acceptance is unavailable no longer describes the integrated application.

## Findings and limitations

### Medium: rejection blocks direct revision until the RFQ is reopened

An independent current-checkout HTTP probe issued v1, rejected it as Customer and then used the Admin create-revision endpoint with expected version 1. The response was **409: “This RFQ is closed or rejected”**.

`decide_quote` marks both the quote and RFQ rejected. `create_draft` rejects any RFQ with rejected status. The quotation UI nevertheless offers **Create revised draft** for the latest rejected quotation. Its request therefore fails. Reopening the RFQ through the existing Admin status endpoint to `under_review` allowed the same revision request to succeed as v2.

This is an incomplete journey rather than permanent data loss: reopening is possible. The quotation action should either support revising an unaccepted rejected offer directly or explain and provide the required reopening step. Current S07 tests verify rejection but stop before the next Admin revision.

### Medium: stale dirty drafts have no in-place recovery action

Source finding in `QuotationWorkspace.jsx`: changing an input sets `dirty=true`. Both toolbar Refresh and error Reload are disabled while dirty; version switching is disabled too. If a competing save/revision causes the next save to return 409, the catch only sets an error. It neither reconciles the new version nor clears dirty state, and there is no discard-draft-edits control.

The Admin cannot use the displayed Reload action to resolve that conflict. They must leave/reopen the workspace or reload the page and lose local work. Preserve the edits or offer explicit discard/reload recovery with the latest state. The backend correctly rejects stale writes; this finding concerns the user recovery flow and was not reproduced in a browser today.

### Medium: UI does not identify tax as sample academic data

The API returns `tax_label: Sample tax (academic demonstration)`. The workspace ignores that field and renders “Tax (%)”, “Tax ({rate}%)” and ordinary price/tax text. It contains no sample/academic tax disclosure. This does not meet the explicit S07/CONTEXT sample-tax labeling requirement, even though the API metadata and calculations are correct. Source-confirmed; no rendered-browser verification today.

### Lower priority: successful write followed by failed refresh yields ambiguous feedback

`mutate` saves, awaits `load(saved.id)`, then sets a success message. `load` catches its own fetch failures without rethrowing. A successful write followed by a failed list refresh can display an error and success together with old local quote data. The failure may be a refresh problem, but that distinction is not explained to the user. On an initial list failure, the screen can also render “No quotation yet” below the load error even though absence was never established.

These are source findings. Verify the write-success/read-failure sequence and use explicit saved-but-refresh-failed feedback rather than treating stale state as reconciled.

### Lower priority: a retried change request creates duplicate decisions

Two identical legitimate `request_changes` submissions produced **two persisted decisions**, with total unchanged. No idempotency key or duplicate suppression exists. The busy state prevents normal duplicate clicks but cannot resolve a lost response followed by a retry. S07 does not explicitly require decision idempotency, so this is a recovery improvement, not a failure of S08's separately required acceptance idempotency.

### Verification remains incomplete

Today's tests prove the ordinary API behavior with SQLite, not PostgreSQL row locking or migrations. The opt-in race tests use `Base.metadata.create_all` in disposable PostgreSQL schemas, so even a passing race run would not independently prove Alembic migration 006. Additional checks are needed for failed-save rollback, decision-versus-revision concurrency, exact expiry boundary, all mutation security matrix rows and current browser recovery states.

## Tests and evidence from this review

Executed from `backend` with bytecode and pytest cache disabled:

```text
.venv/bin/python -B -m pytest -q -ra -p no:cacheprovider tests/test_quotations_s07.py tests/test_quotations_s07_postgres.py tests/test_acceptance_s08.py
26 passed, 3 skipped, 1 warning in 14.76s
```

The 26 passes comprise **14 S07 API cases and 12 S08 acceptance regression cases**, including parameterized cases. The three skips are two version races and one simultaneous-edit race, because `S07_POSTGRES_TEST_URL` was unset. A read-only readiness check also found no PostgreSQL response on `127.0.0.1:5432`. No PostgreSQL environment was provisioned or shared database accessed for this review. Warning: deprecated Starlette/httpx TestClient integration.

`npm --prefix frontend run build` passed using the current custom esbuild build script. Existing installed dependencies were used; no clean install or CI execution is claimed. Python was 3.12.16.

An independent inline HTTP probe used a new in-memory SQLite schema and per-request SQLAlchemy sessions, with separate Admin/Customer clients and privately generated synthetic credentials. It did not import pytest fixtures or modify application files. Results:

- ₹0.05 at 10% sample tax produced tax **₹0.01**, total **₹0.06**, manual source and null estimate reference.
- Two repeated change requests saved two decisions, preserving total.
- Revision immediately after Customer rejection returned 409.
- Explicit RFQ reopening followed by the same revision succeeded with 201/v2.

The [existing S07 evidence record](../S07_VERIFICATION.md) reports earlier local PostgreSQL races, migration 001–006 and native Safari workflows, plus a follow-up for RFQ-based creation. Those are historical evidence, not reruns against today's revision. Its whole-suite count and incomplete phone/empty/error/hosted checks must not be converted into current blanket acceptance.
