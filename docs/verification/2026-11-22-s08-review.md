## What S08 was supposed to deliver

Sources: [CONTEXT](../CONTEXT.md), [master PRP](../PRP.md), [S08 slice specification](../VERTICAL_SLICE_PLAN.md#s08--accept-once-inspect-invoice-and-cancel-an-entirely-unpaid-order), [verification obligations](../VERIFICATION_PLAN.md#12-verification-obligations-for-remaining-slices), and the existing [S08 evidence record](../S08_VERIFICATION.md).

Customer accepts the latest eligible offer → one awaiting-payment order and one demo invoice are committed → owner/Admin inspect/download the invoice. A separate zero-payment order can be cancelled.

- Eligibility (owner, latest version, sent, unexpired) checked at action time; concurrent acceptance/revision preserves invariants.
- Quote/order/invoice atomicity; unique order per accepted quote and unique invoice per order; repeat acceptance returns the same records.
- Immutable item/tax/amount snapshots unaffected by later catalogue/profile edits (AC-02-05 recheck with a real order).
- Order/invoice lists/details, invoice download; cancellation only for wholly unpaid orders, preserving history and blocking assignment.
- No payment button until S09; acceptance does not confirm production; no invented job/stage history.

S08 owns REQ-17, initial commercial views of REQ-18, REQ-20, REQ-21; AC-05-02/04 (acceptance portions), AC-05-06 through AC-05-08, AC-06-01, AC-06-06, AC-06-07. It depends on S01 sessions/file access, S02 profiles and S07 quotations; defects recorded in those reviews remain relevant.

## What is good

1. Acceptance re-checks ownership, latest version, sent status and expiry inside the locked transaction, not from client state.
2. Order, snapshot, invoice and initial history commit together; the route rolls back on any exception, so a failed invoice insert leaves the quote sent with no partial records.
3. Duplicate safety is enforced both in code (existing-snapshot return) and in the schema (unique constraints), so retries and concurrent acceptance converge on one pair.
4. Issued commercial values are copied from the quote rather than recalculated from catalogue or settings, satisfying the immutability intent of AC-06-06/AC-02-05.
5. Cancellation locks the order row; S09 payment recording locks the same row, so cancellation and first payment serialize instead of racing.
6. Cancellation preserves the invoice (marked cancelled), snapshot, reason and dated history rather than deleting records; reason length is bounded at 500 characters.
7. Production status is explicitly `None`, and Admin assignment is gated on full successful payment — no invented production history.
8. Mutations require trusted Origin and CSRF; invoice download uses the authenticated per-tab file helper established in the S01 follow-up.

## What is wrong or incomplete

### Medium — cancellation retry after a lost response reports failure

A second cancel request on an already-cancelled order returns 409 `ORDER_ALREADY_CANCELLED`. If the first response is lost, the Customer retries and sees "This order is already cancelled" as an error in the modal although the requested outcome succeeded. Acceptance is idempotent; cancellation is not.

**Suggestion:** treat a repeat cancellation by the same owner as success returning the current detail (or have the UI reload and present the cancelled state). Test lost-response retry.

### Medium — RFQ lifecycle is not advanced on acceptance

Acceptance sets the quote to `accepted` but leaves the RFQ at `quoted`; `RFQStatus` has no accepted/ordered state. Rejection does update the RFQ. RFQ lists can therefore present an ordered request as still awaiting a decision.

**Suggestion:** confirm the intended RFQ state after acceptance with the PRP owner and update it within the same transaction if required. Do not invent a new status without authorization.

### Medium — destructive cascades on issued commercial records

`CommercialInvoice.customer_id` uses `ON DELETE CASCADE` to `users`, and snapshot/invoice/history cascade from `orders`. Deleting a user or order row would silently remove issued invoices and history, contrary to the retained-history rule. No application path deleting these was found; the risk is schema-level.

**Suggestion:** prefer `RESTRICT` (deactivation rather than deletion) for issued records, with a migration and retained-record test.

### Medium — PostgreSQL concurrency and migration evidence not reproduced

In this review `test_acceptance_s08_postgres.py` and `test_migrations_s08.py` cases **skipped** because `S07_POSTGRES_TEST_URL` was not set. The concurrent acceptance, acceptance-versus-revision, duplicate-cancellation and 006→007 upgrade claims rely on the earlier record only.

**Suggestion:** re-run against a disposable localhost `_test` database before closure and record the result alongside the revision.

### Low — UI polling hides failures and KPIs follow filters

- `useKpcLiveSync` quiet reloads swallow errors, so an unavailable API leaves stale orders displayed without any indication.
- Order KPI cards are computed from the currently filtered/searched list, so "Total Orders" changes with the filter.
- Search is applied in Python after loading all matching rows; acceptable at demo scale, but unpaginated.

**Suggestion:** show a non-intrusive stale/unavailable indicator after failed background refreshes; compute KPIs from unfiltered data or label them as filtered.

### Low — snapshot details

- Item unit is always `pcs`; acceptable while quotation items have no unit, but should not be presented as captured data.
- Legacy `pending_payment` orders count as awaiting payment yet are not cancellable without a snapshot; UI states "Eligible for cancellation if unpaid", which may confuse for legacy rows.
- `create_order_and_invoice_atomic`'s idempotency pre-check is unlocked; safety relies on callers holding the RFQ lock plus unique constraints. Any future caller must preserve that.

### Dependency and release gaps

- Hosted Vercel/Render acceptance → download → cancellation remains pending per the S08 evidence record.
- S01 inherited session findings (JavaScript-readable credential, stale-auth recovery) still apply.
- Fresh desktop/mobile browser verification of the closure follow-up was not completed in the original record either.
