# S02 implementation and verification review

Date: 17 November 2026. Reviewed checkout: `2ed95a8`, with pre-existing untracked verification files. No application source was changed. This review adds this report; the frontend build regenerated ignored build artifacts.

**Assessment: S02 is partially implemented and is not ready to close.** Registration, Customer/Employee profile editing, Admin employee creation, status changes, password reset and password change exist. Mandatory password change is not enforced, invalid profile input is insufficiently validated, and Admin self-service is incomplete. Passing existing tests does not establish acceptance.

## 1. What was supposed to be implemented

Sources: [S02 slice scope](../VERTICAL_SLICE_PLAN.md#s02--register-maintain-profiles-and-manage-account-access), [PRP-001](../PRPs/001-accounts-and-access.md), [approved context](../CONTEXT.md), and [verification obligations](../VERIFICATION_PLAN.md#12-verification-obligations-for-remaining-slices).

The expected journey is: Visitor registers a Customer and associated business profile atomically, signs in, and maintains permitted business details. Admin creates an Employee, who can sign in and maintain permitted personal details. Admin can activate/deactivate accounts or reset passwords. Reset invalidates previous sessions and requires password change before normal work resumes. Self-password change invalidates existing sessions and requires fresh login.

Required boundaries:

- Public registration creates Customer accounts only; one customer login owns one business profile.
- Self-profile changes cannot alter role, activation, another user's profile, or Employee employment facts such as department.
- Signed-in Customer, Employee **and Admin** can maintain their permitted profile/password under REQ-03.
- Invalid or failed updates preserve stored state and give useful field feedback; duplicate/invalid registration leaves no incomplete user/profile pair.
- Deactivation, reset and password change invalidate affected sessions while retaining identities and operational links.
- Backend authorization applies to direct requests. Protected mutations inherit S01 Origin/CSRF rules, and errors/secrets follow the shared requirements.
- Profile images are explicitly deferred to S06. Invitations, email reset delivery/verification, suppliers, configurable roles and two-factor authentication are excluded.

S02 owns REQ-01, REQ-03 and REQ-04; AC-01-01/02/06/07/08 and the reset/deactivation portion completing AC-01-04. It depends on S01, whose unresolved session/UI findings remain relevant regression concerns.

## 3. Findings

### High — mandatory password change can be bypassed

After Admin reset, an isolated client signed in with the reset password and received `must_change_password=true`. Before changing password, it successfully submitted `PATCH /api/profile/me`: **200**, and the new company name persisted.

`get_current_user` returns the session owner without checking the flag; role guards and ProtectedRoute do not restrict temporary-password sessions. Customer/Employee portals show a warning while continuing to render normal work. This directly contradicts AC-01-08 and the requirement to change password before normal work resumes. The existing reset test verifies only old-session revocation and the flag, not actual enforcement.

The earlier PostgreSQL audit on `564d52e` also recorded successful RFQ creation before changing a reset password. This review reproduced the underlying restriction failure on the current checkout through profile editing, using SQLite; it does not claim a new PostgreSQL RFQ run.

### Medium — whitespace-only registration values create invalid business profiles

An isolated registration with spaces for company/contact and seven spaces for phone returned **201** and stored all three as empty strings. Length checks run before the service trims values. This violates invalid-registration expectations in AC-01-02. Employee full-name creation follows the same trim-after-validation pattern and needs equivalent boundary coverage; this review did not execute that particular creation variant.

### Medium — the profile route bypasses bounded profile schemas

Although `CustomerProfileUpdateRequest` and `EmployeeProfileUpdateRequest` declare lengths, the route uses generic `ProfileUpdateRequest`, whose string fields have no length constraints. A current-review request containing a 256-character company name and one-character phone returned **200** in SQLite and stored those lengths.

SQLite does not enforce the PostgreSQL `VARCHAR(255)` limit. The historical PostgreSQL audit recorded **500** for a 256-character company name. This review confirms the missing request validation, rather than claiming that PostgreSQL 500 was rerun. The consequence is either invalid stored data or an uncontrolled database error instead of actionable validation. Required blank profile edits can also be silently ignored with success rather than rejected as invalid.

### Medium — Admin self-profile and normal password-change entry are incomplete

An Admin request to update own full name/phone returned **200**, but a subsequent read contained no submitted personal details. `update_own_profile` implements Customer and Employee branches only. No Admin self-profile form was found.

AdminPortal imports and renders PasswordChangeModal, but the only calls to `setIsPasswordModalOpen` found are initialization and closing; there is no opening control. Admin can reach the backend change-password endpoint directly, but cannot complete the normal self-service password journey through the current UI. REQ-03 explicitly includes Admin. Its permitted personal fields should be made explicit in implementation/verification without inventing a new role or employment model.

### Medium — validation feedback and confidentiality inherit S01 defects

There is no shared normalized validation exception handler. Frontend forms usually read `detail.message`, whereas default validation errors are lists, so they fall back to generic feedback without identifying affected fields. The S01 review independently reproduced malformed password input echoed in a validation response. S02 password/registration schemas use the same default validation machinery; sanitization and field-level feedback need verification across these endpoints. No new S02 secret-echo probe was run here.

### Verification gaps and lower-priority observations

- Employee department tampering returned 200 while preserving the original department. This demonstrates no privilege change, but gives no explicit denial; the expected feedback should be recorded rather than calling the response an accepted department update.
- Admin user list counts every stored session row without filtering expiry, despite naming the count `active_sessions_count`. Expired rows not yet visited can therefore inflate this display. This is source-derived and was not reproduced in a browser.
- Employee UI substitutes “Pattern Tooling & Machining” for an absent department. Customer UI substitutes an Ahmedabad address when absent. These can present invented profile facts rather than an honest empty state; source review only.
- Duplicate-account checks precede insert; no handled `IntegrityError` path was found for overlapping registrations/employee creation. Ordinary duplicate rejection works, but concurrent conflict feedback/atomicity is unverified. This is not a claim that duplicate rows were reproduced.
- S01's frontend expiry/logout recovery issues affect users whose sessions are revoked by S02. Backend denial alone does not establish that an already-open browser clears stale identity and offers useful recovery.

## 7. Completion decision

**Keep S02 open.** The principal journeys exist, but AC-01-08 fails, AC-01-02/06 have validation defects, and REQ-03 Admin self-service is incomplete. The full verification contract and real PostgreSQL/browser/failure-recovery evidence are also missing.

Before closure, implement the missing restrictions/self-service and validation behavior; expand the S02 contract against the existing AC IDs; run the required isolated PostgreSQL and browser checks plus relevant S01 regression checks; and record expected/actual outcomes with current revision, dependency/migration versions, environment and sanitized evidence. No fixes are included in this review.
