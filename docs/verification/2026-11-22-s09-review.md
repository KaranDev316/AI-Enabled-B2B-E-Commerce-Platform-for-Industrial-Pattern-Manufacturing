## What S09 was supposed to implement

Sources: [S09 slice plan](../VERTICAL_SLICE_PLAN.md#s09--settle-a-demo-invoice-safely), [PRP-006](../PRPs/006-orders-payments-and-invoices.md), [approved context](../CONTEXT.md), [verification plan](../VERIFICATION_PLAN.md), and [S09 contract and prior evidence](../S09_VERIFICATION.md).

An owning Customer or Admin records a positive partial payment against an outstanding invoice. Successful installments reduce the remaining balance; failed attempts remain in history without reducing it. Final successful settlement confirms the order and permits subsequent production assignment. Repeating an operation with the same key and details returns the original result.

- Persist payment amount, actor, outcome, idempotency key and timestamp.
- Use Decimal INR; outstanding equals issued total minus successful payments. Reject zero/negative/invalid amounts and overpayment.
- Reject reused keys with different invoice, amount or outcome; prevent duplicate payments and overpayment under concurrency.
- Commit ledger, cached settlement, invoice state and order confirmation together, or roll them all back.
- Serialize payment and unpaid cancellation against the same order state. Failed attempts alone do not block cancellation; any successful partial/full payment does. Cancelled orders cannot receive new payments.
- Keep accepted items, sample tax and original totals unchanged while history and settlement evolve; download reflects the same snapshot and current payment history.
- Apply session, ownership, Origin and CSRF protections to real endpoints. Collect no real card, bank or UPI credentials.
- Preserve an uncertain operation's exact key/details across retry/reload, lock its inputs, and never automatically replay it after login.

S09 owns REQ-19 and payment-sensitive completion of REQ-20/21; AC-06-03 through AC-06-08. Actual job creation is S10. Gateways, real credentials, refunds, reversals and 60/40 milestones are excluded.

The original scope requires visible simulation/academic wording. The later **Product wording and PDF follow-up** in S09_VERIFICATION explicitly records that the task owner requested its removal from payment/order/invoice surfaces. Current product wording follows that recorded exception; this review does not call it an unauthorized change or request its reversal. ## What is working well

The service checks access before exposing an existing attempt. Its matching-retry lookup precedes the new-payment eligibility check, allowing a legitimate retry to retrieve a successful final installment or an earlier failed attempt even after cancellation. Conflicting reuse is rejected rather than silently reinterpreted.

Payments and cancellation lock the same order row. Settlement uses a successful-payment ledger, with cached-balance mismatch treated as unavailable rather than silently repaired. A full payment records confirmation once; partial settlement stays awaiting payment and blocks cancellation/assignment. Issued item/tax/total snapshots are not recalculated by the payment service.

The frontend saves an operation before sending, scopes it by user/invoice in tab storage, disables changes while it is unresolved, and preserves it for 401/403/network/server uncertainty. A paid or cancelled invoice can still display a pending-operation retry. Known failed outcomes are shown separately from successful settlement. These are useful safeguards beyond a basic payment button.

## Findings and remaining gaps

### Medium: Customer payment refresh failure is hidden

Source finding: after a known payment response, DemoPaymentForm calls `onRecorded` and has a catch intended to show “Payment result saved. Refresh the invoice…”. The Customer callback calls `openInvoiceDetail(id, true)` and `loadInvoices({quiet:true})`, but both functions catch retrieval failures internally and do not reject. The form's refresh-failure message is therefore not reached for those failures.

The UI can show a correctly recorded payment alongside an old paid/outstanding/history view without saying the refresh failed. This does not prove duplicate settlement: the backend still prevents overpayment. Preserve quiet polling without flicker, but distinguish a stale invoice after an explicit payment action. Verify API write success followed by detail/list read failure and recovery.

### Medium: Admin detail errors are presented as lack of selection

The initial Admin detail fetch catches failure by setting `detail=null`; the rendering then says “Select an invoice to inspect its immutable commercial snapshot” even when an invoice is already selected and its request failed. No detail-specific error/retry appears. Background detail refresh failures only log a warning while leaving old values visible.

This gives misleading state after retrieval failure and affects payment/history inspection. Add or verify a clear detail-error/retry state while retaining previously loaded data for transient background failures. This is a source-confirmed UI handling gap, not a new browser reproduction.

### Lower priority: Admin invoice selection is pointer-only in the table

Invoice rows use an `onClick` handler without a keyboard-focusable button/link, `tabIndex`, or keyboard handler. A keyboard user cannot select another row through the table's current controls. This is visible in source; native keyboard and focus testing remain outstanding.

### Traceability: product wording differs from original demonstration-label requirements

Current form/PDF use ordinary payment/invoice wording. The evidence record attributes that to an explicit owner request. Keep this as a documented scope exception, with the still-simulated behavior and absence of real financial integration clear in project acceptance records. The outcome selector is not evidence of a real gateway.

### Verification gap: concurrency and migration were not rerun

The five real PostgreSQL race tests and migration test require `S07_POSTGRES_TEST_URL`. It was unset, and a readiness check found no PostgreSQL response on localhost port 5432. Those cases skipped. The SQLite tests cannot establish PostgreSQL row-lock serialization or Alembic 007→008 preservation.

The existing S09 record reports earlier successful PostgreSQL tests, shared migration 008 activation and a later narrow/desktop Customer polling check. These are historical observations, not new verification of deployed state or a full owner/Admin browser payment walkthrough today. This review did not inspect or modify Supabase or restart the normal application.
