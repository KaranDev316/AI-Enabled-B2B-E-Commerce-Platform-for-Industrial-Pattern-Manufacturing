# S01 implementation and verification review

Date: 17 November 2026. Reviewed checkout: `2ed95a8` plus the pre-existing untracked audit files. Application code was not changed. This review adds only this report; running the build regenerated ignored frontend build artifacts.

**Assessment: S01's core authentication implementation exists, but S01 is not ready to close.** Targeted tests pass, but the full verification contract is incomplete and there are defects in validation confidentiality and frontend session handling.

## 1. What was supposed to be implemented

The controlling slice is [S01 in the vertical slice plan](../VERTICAL_SLICE_PLAN.md#s01--sign-in-enter-the-correct-portal-and-sign-out), supported by [PRP-001](../PRPs/001-accounts-and-access.md) and [the verification plan](../VERIFICATION_PLAN.md).

An active Customer, Employee, or Admin should sign in, enter only their own portal, retain the session during normal navigation/refresh, and sign out. Wrong credentials and inactive accounts should receive the same generic failure. Expired or revoked credentials must grant no protected access.

Required implementation also includes:

- Python 3.12/FastAPI and Node 24/React application foundation; relative same-origin API calls and a Vite development proxy.
- PostgreSQL users/sessions, initial Alembic migration, Argon2id hashes in `VARCHAR(255)`, initial Admin setup, and controlled synthetic Customer/Employee identities with any necessary profile foundations.
- Server role guards, login session rotation, configurable expiry through `SESSION_TTL_SECONDS`, and server-side logout revocation.
- HttpOnly, SameSite=Lax cookies; Secure cookies on hosted HTTPS; trusted-Origin checks on login and mutations; session-bound CSRF on authenticated mutations including logout.
- Shared minimal portal shells, loading/error/denied states, safe handling of network/database failure, and no invented dashboard data.
- Isolated PostgreSQL verification, backend CI checks, frontend build, and a small Render/Supabase demonstration under one HTTPS origin, including migration and restart evidence.

S01 owns REQ-02, AC-01-03, AC-01-05, and the logout/expiry portion of AC-01-04. Registration, profile editing, employee management, password reset/change journeys, and the Admin deactivation interface belong to S02. Their existence or defects must not be mistaken for S01 completion evidence. The S01 fixture check for an account becoming inactive is still required.

## 3. Defects and gaps

### High: frontend treats failed logout as completed logout

`frontend/src/context/AuthContext.jsx:81` awaits `fetch` without checking `response.ok`, catches network failures, and always clears local identity/CSRF in `finally`. `frontend/src/components/PortalLayout.jsx` then navigates to login regardless of server outcome.

A 403, 500, or unreachable API can therefore leave the server session/cookie usable while the UI appears signed out. Refresh can resolve that still-valid session again. This contradicts honest failure/retry behavior in V20 and B12 and undermines the logout journey. This is a source-confirmed defect; this review did not run a browser failure-injection reproduction.

### High: malformed password input is echoed in validation responses

A direct TestClient check submitted a synthetic string inside a password array. The response was HTTP 422 and included that submitted password input in the default validation error. The response is not the required normalized code/message/optional-field-errors structure.

This directly fails V03's no-echo condition and the validation format requirement. The existing V03 test checks only status 422 for two inputs and consequently misses the issue. No real password was used or recorded.

Reproduction used an override yielding `None` for `get_db`, so the request could reach validation without a configured live database; the invalid body never enters login. This proves HTTP validation behavior, not database integration. An initial attempt without the override could not produce a JSON validation response in the unconfigured database environment and was not treated as evidence for the defect.

### Medium: expired/revoked sessions do not consistently clear authenticated UI

`AuthContext` resolves the session only on initial mount and explicit login/logout. There is no shared 401 handler or session refresh mechanism. For example, `CustomerPortal.fetchMyRfqs` ignores a non-OK response; `AdminPortal.fetchUsers` gives a generic failure without clearing auth state. ProtectedRoute continues trusting the in-memory user, and PortalLayout displays “Session Active · Server Verified”.

The backend guard should still deny fresh protected requests; this finding does not establish a backend authorization bypass. The UI can retain stale identity/data and fail to prompt for login after expiry or another tab's logout. B06/B07 require this lifecycle to be verified and corrected where it fails. Source review establishes the missing handling; browser reproduction remains outstanding. A real-time cross-tab notification system is not required.

### Medium: session lookup failures are indistinguishable from signed-out state in the UI

On initial `/auth/me`, any non-OK response or network exception clears identity and finishes loading without reporting service failure. Users are sent to login even if the session service is merely unavailable. This does fail closed, but does not provide the distinct failure/retry feedback required by the operation contract and B12.

### Verification gap: SQLite auth tests cannot close PostgreSQL requirements

`backend/tests/conftest.py` constructs an in-memory SQLite schema with `Base.metadata.create_all`. It does not apply Alembic or use `TEST_DATABASE_URL`. The separate database test checks connectivity only. Thus green CI cannot establish PostgreSQL session transactions, migrations, provisioning or persistence across API restarts.

### Documentation and provisioning gaps

README still says authentication, migrations, and tables do not exist. The verification plan is a specification whose original status says NOT RUN, not an updated execution ledger. There is no complete per-case S01 closure record. A reproducible privately configured demo-role setup and hosted startup/migration procedure were not established from the inspected files. Admin CLI accepts the password as a command-line argument; secure credential delivery and rerun/session-invalidation behavior warrant review before treating provisioning as complete evidence.

## 7. Completion decision

**Keep S01 open.** The contract requires passing evidence for all 26 V cases and 12 B cases, all applicable matrices, real PostgreSQL migrations/persistence, isolated CI, development-proxy browser behavior, hosted HTTPS cookies and restart behavior. That evidence is not available, and the validation/failed-logout/session-recovery defects remain unresolved.

Before closing S01, address the identified S01 defects; complete reproducible private role provisioning and operating instructions; run the missing PostgreSQL, failure-injection, browser and hosted checks; and record per-case expected/actual outcomes with current revision, runtime/dependency/migration versions, environment and sanitized evidence. Update the stale implementation status in project documentation as a separate authorized implementation task. No fixes are included in this report.
