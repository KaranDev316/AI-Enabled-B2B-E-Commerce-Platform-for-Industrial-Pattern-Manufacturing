# S04 implementation review

Date: 22 November 2026. Reviewed revision: `ecc81b7`. The existing untracked S01–S03 reports were preserved. This task adds only this report. Application files, configuration, dependencies, existing documentation, and design assets were not edited.

**Assessment: S04 has a strong backend implementation and useful failure tests, but should remain open.** Product/category maintenance, activation, image validation, private storage integration, and compensation exist. Frontend refresh honesty, stale updates, storage error classification, reference alignment, and missing persistent/browser acceptance evidence remain concerns.

## What S04 was supposed to deliver

Sources: [CONTEXT](../CONTEXT.md), [master PRP](../PRP.md), [PRP-002](../PRPs/002-public-catalogue-and-products.md), [S04 slice scope](../VERTICAL_SLICE_PLAN.md#s04--maintain-catalogue-products-and-images), [verification obligations](../VERIFICATION_PLAN.md#12-verification-obligations-for-remaining-slices), and [S04 implementation notes](../implementation/S04-CATALOGUE.md). Requirements govern behavior; implementation notes are supporting evidence, not authority to change scope.

Admin adds/edits categories and products, uploads valid images, and sees saved details in the public catalogue after refresh. Deactivation removes a product from new public selection without deleting historical references or changing accepted commercial snapshots.

Required boundaries:

- Active Admin authorization on management APIs, including direct requests; trusted Origin and session-bound CSRF on mutations.
- Validated product/category/specification/material/indicative-price fields. Missing price means on request. Invalid or failed saves preserve stored state and user input.
- JPG/JPEG/PNG only, at most two files per submission and 20 MB per file. Generated storage keys, backend content checks, private persistent storage, and cleanup after partial storage/database failure.
- Public imagery belongs only to active catalogue products. Customer documents remain private. Missing imagery has an honest fallback.
- Migration upgrades retain existing records. UI follows the supplied Admin product-management reference and established shell.

S04 covers REQ-06, upload/write portions of REQ-07, AC-02-04/05/06. AC-02-05 requires later integration with actual accepted commercial records in S08. There are no suppliers, purchasing, destructive deletion of referenced products, or image-generation features in scope.

## What is good

1. Backend access control is centralized on the management router, and authenticated mutations use both Origin and CSRF checks. Tests include direct unauthorized requests.
2. Product validation is stronger than S02's profile validation: text is trimmed before constraints, malformed slugs and invalid prices fail, and unknown categories are rejected.
3. Upload validation checks filename extension, declared MIME, actual format, image integrity, bytes, and pixel count. Every submitted file is validated before storage writes begin.
4. Random catalogue-only keys avoid trusting filenames as storage paths. Original filenames are reduced to a basename and limited in metadata; public responses omit storage keys.
5. Product details and images are separate saves, with explicit UI wording. A failed image upload does not pretend the already-saved product details were rolled back.
6. Tests cover two-image success, second-write failure, database metadata failure, preservation of existing images, rejected invalid files, and safe remote error messages. This is substantive failure coverage.
7. Deactivation preserves the product record and a tested RFQ reference. Public reads and public image reads enforce active status; Admin can still preview inactive imagery.
8. Protected Admin previews use the existing authenticated file helper, with loading/error/retry behavior and object-URL cleanup.

## What is wrong or incomplete

### Medium — refresh errors are swallowed and overwritten by success

`AdminCatalogue.load()` catches failures and stores an error notice, but does not throw or return a failure result. Product/category save, activation, upload, and removal handlers await it and then overwrite its error with a success notice. The mutation may have committed, yet the screen can show stale records with no indication that verification/refresh failed. Initial load failure can also show an error alongside an empty/no-matches table, rather than a distinct unavailable state.

**Suggestion:** track mutation success separately from refresh success, preserve an honest refresh-failed notice, and expose retry through the existing refresh control. Keep failed editor input intact. Test successful mutation followed by failed refresh and subsequent recovery. This finding is source-confirmed; browser failure injection was not performed.

### Medium — activation can overwrite unrelated edits from another Admin/tab

`toggleProduct` sends the entire product copied from the currently loaded row as a PUT body. If another Admin changed its description, specifications, price, or name meanwhile, activation/deactivation sends old values for those fields. Backend row locking serializes writes but does not reject stale payloads.

**Suggestion:** make activation update only the intended state, or use a version check and conflict feedback for stale edits. Test two independent sessions editing and toggling the same product. This is a source-derived lost-update risk; no concurrent PostgreSQL reproduction is claimed.

### Medium — image-storage outage is classified as missing image

`CatalogueStorage` inherits `StorageService.get_file`. That method tries two remote paths and raises `FileNotFoundError` whenever neither returns 200, including upstream 401/403/503. Image routes convert that exception to **404**.

A current isolated probe mocked both remote responses as **503** and observed **FileNotFoundError after two attempts**. Thus a storage outage can be presented as missing imagery rather than unavailable storage. No real Supabase request was made.

**Suggestion:** classify actual missing objects separately from authentication/configuration errors and remote outages; return safe, useful unavailable feedback and allow retry. Do not expose service credentials or raw remote responses.

### Medium — management screen departs from the supplied reference

The product-management reference uses one main table with thumbnail/name, Category, Material, Indicative Price, Status and Actions, with search/category/status filters. Current source uses an eight-column-width table beside a persistent category editor, omits image/price columns and category filtering, and combines material beneath the name. It has Edit/Activate controls but no per-product public-view action.

Category maintenance is required, but does not by itself authorize replacing the reference's main table proportions. The source differences are observable; rendered spacing/overflow were not measured.

**Suggestion:** preserve the established Admin shell and restore the reference's principal table/filter hierarchy. Integrate required category editing without replacing that hierarchy. Keep unsupported mockup controls and sample records excluded. No redesign or implementation change is included here.

### Verification risk — case-insensitive category uniqueness is only a pre-check

The service compares lowercase names, while the model declares an ordinary unique constraint on `Category.name`. No case-folded unique index was established in the inspected migrations. Under concurrent PostgreSQL requests, differently cased duplicates can pass the pre-check and ordinary case-sensitive uniqueness.

**Suggestion:** if case-insensitive uniqueness is the intended rule, enforce it in PostgreSQL and test overlapping create/rename requests. Exact duplicate slug/name conflicts are handled with rollback/409, but this does not close the case-variant race. No duplicate race was executed here.

### Other issues and practical limitations

- Many API failures use a string `detail`, rather than the shared code/message/optional-field-errors structure. The Admin request helper handles strings and validation lists reasonably, but the API contract remains inconsistent.
- Upload errors instruct application users to edit `.env`, run Alembic, or inspect terminal output. Preserve useful operator diagnostics in logs/documentation and give the Admin concise actionable retry/contact feedback in the product UI.
- Failed cleanup is logged, not durably queued. This is an explicit limitation of compensation, not proof of a broken saved association. Test cleanup failure and record the operator reconciliation procedure before claiming complete storage cleanup.
- The two-file rule is per submission. The code permits additional later submissions; this matches the stated S04 rule and should not be misreported as a missing two-images-total limit.
- The 20 MB convention is implemented as **20 × 1024 × 1024 bytes**. The additional 25-megapixel safety limit is explicit in code and implementation notes; document it in acceptance evidence and verify boundary behavior.
- Existing S04 notes contain stale port-8000 startup instructions and claim reference-photo fallbacks. Current proxy targets port 8001 and live catalogue uses an honest missing-image fallback. Do not follow historical setup instructions blindly or restore invented product imagery.

## Suggested next steps

1. Correct refresh/error honesty and image-storage status classification.
2. Prevent activation from overwriting unrelated stale fields; enforce intended category uniqueness under concurrent writes.
3. Bring the existing management table/filter presentation back into alignment with the reference, without replacing routes or the Admin shell.
4. Complete per-operation authorization, invalid edit/state-preservation, exact upload boundaries, malformed/truncated/oversized-pixel images, and compensation/deletion failure checks.
5. Run isolated PostgreSQL migration upgrade/repeat/restart and concurrent updates. Exercise actual private Supabase storage and preserve images across API restart.
6. Demonstrate accepted-history preservation using a product actually linked through the RFQ/quotation/order workflow. Record that catalogue changes do not modify official snapshots.
7. Record desktop/mobile browser create/edit/filter/category/upload/preview/remove/deactivate/reactivate and error/retry journeys, then hosted release checks. Update stale setup/evidence documentation in a separately authorized task.
